A tool is the smallest unit of effect. It never decides when to run; something else decides, and the tool does exactly one thing.

Tools are the most under-designed part of most agent systems. A model's judgement is only as trustworthy as the actions it can take, and an action is only as safe as its contract.

## Every tool declares five things

| Field | Why it exists |
| --- | --- |
| **Input schema** | The agent must be able to see what a valid call looks like, and fail before acting rather than during |
| **Output schema** | What comes back, including what failure looks like |
| **Cost** | Money, latency and side effects — consumed from the caller's budget |
| **Risk class** | How much damage a wrong call can do, and therefore who may call it |
| **Reversibility** | Whether a mistake can be undone, and by whom |

The last two are the ones people omit, and the two that matter most. `read_file` and `delete_production_database` are not the same kind of thing, and a system that treats them the same is one bad token away from an outage.

## Risk classes

<CardGroup cols={2}>
  <Card title="R0 — Read" icon="eye">
    Observes only. No side effects. Safe to let any agent call at any autonomy level.
  </Card>
  <Card title="R1 — Reversible write" icon="rotate-left">
    Changes state that can be restored: a draft, a ticket comment, a staging deploy.
  </Card>
  <Card title="R2 — Consequential write" icon="triangle-exclamation">
    Changes state with real cost: a customer email, a price change, a production config.
  </Card>
  <Card title="R3 — Irreversible or external" icon="radiation">
    Money moves, data leaves, physical action occurs, or something is deleted for good.
  </Card>
</CardGroup>

Autonomy and risk compose. An L5 agent may call R0 and R1 freely; R2 requires a contract that names the action; R3 requires an explicit approval gate no matter how high the autonomy level. See [Autonomy](/intelligence/autonomy).

## Design rules

**One action per tool.** A tool called `manage_user` that can create, delete or promote is three tools wearing a coat. Split it, and the risk classes become meaningful.

**Make the failure explicit.** An agent that receives a clean error can re-plan. An agent that receives an empty success believes it worked.

**Never encode policy in the tool.** "Refuse if the customer is in the EU" belongs in the contract or the arbiter, not inside a tool that another agent might bypass. Policy in a tool is policy that only applies to callers of that tool.

**Idempotency where possible.** Agents retry. A non-idempotent tool plus a retry policy equals duplicate side effects, and duplicate side effects are how a helpful agent sends the same refund three times.

<Warning>
  A tool's description is prompt surface. An agent chooses tools based on what the description says, so a stale description produces confidently wrong tool choices. Treat the description as code: version it, review it, and change it when behaviour changes.
</Warning>

## Tool poisoning

Any tool that fetches external content — a web page, an email body, a document — can carry instructions. A tool result is not a trusted message; it is untrusted input that happens to arrive in a system channel.

Omenra treats tool output as data, never as instruction. Anything that looks like a directive inside a tool result is surfaced to the agent as text to reason about, not authority to obey. This is one of the reasons the [contract](/intelligence/autonomy) exists separately from the prompt: instructions that arrive through a tool cannot widen it.
